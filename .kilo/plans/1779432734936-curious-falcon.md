# Plan: PF2e Support And System Selection

## Context Read

- Read `CONTEXT.md` and root `AGENTS.md` as required.
- No separate lowercase `agent.md` exists in the repository.
- Relevant current files inspected: `scripts/settings.mjs`, `scripts/constants.mjs`, `scripts/utils/hp-resolver.mjs`, `scripts/logic/AutoActivation.mjs`, `scripts/module.mjs`, `scripts/apps/MultiTokenArtManager.mjs`, `scripts/apps/SettingsPanel.mjs`, `templates/settings-panel.hbs`, `lang/en.json`, `lang/ru.json`, `module.json`, `scripts/utils/flag-utils.mjs`.

## Findings

- HP settings currently exist only as raw path settings: `hpCurrentPath` and `hpMaxPath`.
- `applySystemPresetIfNeeded()` already includes `pf2e`, but it is tied to `game.system.id` and only updates paths when both HP settings are still defaults.
- There is no module setting for choosing the target game system.
- There is no first-run setup prompt.
- Status automation currently reads `ActiveEffect`, `tokenDoc.effects`, and `tokenDoc.hasStatusEffect()`, but PF2e conditions are commonly embedded actor `Item` documents of `type: "condition"`, not ordinary ActiveEffects.
- Status change hooks currently listen only to `createActiveEffect`, `updateActiveEffect`, and `deleteActiveEffect`; PF2e condition item changes will not trigger automation reliably.
- Status options in the image settings panel are global DnD-like labels from `STATUS_CONDITIONS`; PF2e needs PF2e condition slugs/names.
- There are no project-local tests found outside dependency files in `node_modules`.

## Implementation Plan

1. Add system selection constants.

- Extend `SETTINGS` in `scripts/constants.mjs` with:
  - `SYSTEM_MODE`, for the selected module system/preset.
  - `SYSTEM_PROMPTED`, to remember that first-run selection was shown for the world.
- Add system mode identifiers, likely `auto`, `dnd5e`, `pf2e`, `wfrp4e`, `custom`.
- Keep existing HP path settings for advanced/manual override compatibility.

2. Create a small system-support layer.

- Add a new module, likely `scripts/system-support.mjs`, to centralize:
  - supported system presets,
  - HP path presets,
  - status option lists,
  - selected system resolution (`auto` resolves to `game.system.id` when supported),
  - PF2e condition extraction helpers,
  - status value normalization for matching.
- Include PF2e HP preset as `system.attributes.hp.value` / `system.attributes.hp.max`.
- Include PF2e condition options using stable slug-like values and readable labels, for example: `blinded`, `clumsy`, `concealed`, `controlled`, `dazzled`, `deafened`, `doomed`, `drained`, `dying`, `encumbered`, `enfeebled`, `fascinated`, `fatigued`, `fleeing`, `frightened`, `grabbed`, `hidden`, `immobilized`, `invisible`, `observed`, `off-guard`, `paralyzed`, `persistent-damage`, `petrified`, `prone`, `quickened`, `restrained`, `sickened`, `slowed`, `stunned`, `stupefied`, `unconscious`, `undetected`, `unnoticed`, `wounded`.
- Preserve the existing generic/DnD-style status list as the default/custom list so existing actor flags keep working.

3. Register new Foundry settings.

- In `scripts/settings.mjs`, register `systemMode` as a world config setting with choices.
- Register `systemPrompted` as a hidden world setting with default `false`.
- Add `onChange` to `systemMode` so changing the setting from Foundry settings applies the selected preset HP paths immediately when the mode is not `custom`.
- Keep `hpCurrentPath` and `hpMaxPath` visible/configurable for custom or advanced use.
- Update `applySystemPresetIfNeeded()` to use the selected module system rather than only `game.system.id`.
- Avoid overwriting custom HP paths unexpectedly when `systemMode === "custom"`.

4. Add first-run system selection dialog.

- Add a function in `scripts/settings.mjs`, for example `showFirstRunSystemDialogIfNeeded()`.
- Call it from the `ready` hook after settings are registered and preset application is possible.
- Show it only to an active GM, because it writes world settings.
- Show it only when `systemPrompted` is false.
- Default the selection to the detected supported system (`game.system.id`) or `auto`.
- Dialog choices should include at least Auto/Detected, D&D5e, PF2e, WFRP4e, and Custom.
- On confirmation:
  - set `systemMode`,
  - set `systemPrompted = true`,
  - apply HP preset for the selected mode unless Custom is chosen.
- On close without selection, mark prompted only if implementation intentionally treats dismissal as completed; preferred behavior is to keep it unprompted so the GM sees it again later.

5. Make HP resolution use system support consistently.

- Update `scripts/utils/hp-resolver.mjs` to get paths through the new system-support helper or through current settings after preset sync.
- Keep fallback to `system.attributes.hp.value` / `system.attributes.hp.max`.
- Optionally add small numeric guards so missing PF2e values do not produce `NaN` and percent stays `0` when max is invalid.

6. Add PF2e condition extraction and matching.

- Move or refactor the current `getTokenStatuses()` logic out of `findBestImageForHp()` into a helper in `AutoActivation.mjs` or the new system-support layer.
- Preserve current extraction from ActiveEffects and token effects.
- Add PF2e extraction when resolved system is `pf2e`:
  - `actor.itemTypes?.condition`, if available,
  - `actor.items` filtered by `item.type === "condition"`,
  - `actor.conditions`, if the PF2e API exposes it as an iterable collection.
- For each PF2e condition, collect multiple match keys:
  - `item.slug`,
  - `item.system.slug`,
  - `item.name`,
  - `item.id`,
  - possibly `item.system.value.value` only as metadata if needed, not as the main key.
- Implement normalized matching so saved values and detected statuses match across case, spaces, underscores, and hyphens. This keeps older status labels working while enabling PF2e slug values.

7. Trigger automation for PF2e condition item changes.

- In `scripts/module.mjs`, add hooks for `createItem`, `updateItem`, and `deleteItem`.
- Resolve the parent actor from `item.parent` when `item.parent.documentName === "Actor"`.
- Only schedule automation when the item is a PF2e-like condition item, i.e. `item.type === "condition"`; optionally guard this by resolved system `pf2e` to avoid noise in other systems.
- Respect the existing `options?.mtaManualUpdate` guard on update.
- Keep existing ActiveEffect hooks unchanged for DnD/generic systems.

8. Update status options in the manager UI.

- In `MultiTokenArtManager._prepareContext()`, replace direct use of `STATUS_CONDITIONS` with system-support status options for the current resolved system.
- Build options as `{ value, label, selected }`.
- Store stable `value` in `autoEnable.status`.
- Include the saved status as an extra option if it is not in the current preset list, so switching systems does not hide or silently erase existing actor configuration.
- The existing `templates/settings-panel.hbs` can probably remain unchanged.

9. Localize new UI strings.

- Add `lang/en.json` and `lang/ru.json` keys for:
  - system setting name/hint,
  - HP path setting names/hints if touched,
  - first-run dialog title/content/buttons,
  - system choice labels: Auto, D&D5e, Pathfinder 2e, WFRP4e, Custom.
- Keep new strings in both language files.

10. Update technical map if implementation changes architecture.

- Update `CONTEXT.md` after implementation because this adds a new system-support layer, new settings, and PF2e condition item hooks.
- Note the new `systemMode` / `systemPrompted` settings and PF2e status handling.

## Verification Plan

- Run a syntax/import sanity check if available; this repo does not appear to have project-local tests.
- Manual Foundry checks in a PF2e world:
  - On first GM ready after install, system selection dialog appears.
  - Selecting Pathfinder 2e sets the module system setting and HP paths.
  - Changing HP on a PF2e actor triggers wounded/dead token and portrait automation.
  - Adding/removing/updating PF2e conditions triggers status automation.
  - Status dropdown shows PF2e condition choices.
  - Existing DnD/generic status automation still works via ActiveEffects.
  - Custom mode keeps manual HP path settings.

## Risk Notes

- PF2e condition document shape can vary by PF2e version, so extraction should be defensive and collect several possible slug/name fields.
- First-run dialog must be GM-only to avoid player permission errors writing world settings.
- Do not alter actor/token flag data shape for images; only interpret `autoEnable.status` more flexibly.
