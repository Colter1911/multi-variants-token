# План: убрать обрезку manual token при Dynamic Ring

## Цель

При ручном создании токена без кастомной рамки, когда итоговый token image остается с включенным Dynamic Ring, не обрезать части изображения/alpha-добавок, выходящие за квадрат базового превью. Поведение должно быть аналогично custom frame: экспортировать overflow-aware canvas и затем компенсировать увеличенный размер через масштаб токена/кольца.

## Найденная причина

- `scripts/apps/MultiTokenArtManager.mjs` сейчас включает overflow-путь только если есть `customFrameConfig`:
  - final export: `#onCreateManualToken()` / `onCreate`, строки около `1884-1903`;
  - preview: `#renderManualTokenPreview()`, строки около `2625-2665`.
- В `scripts/logic/AutoTokenService.mjs` нужная механика уже есть:
  - `_renderTokenCanvasFromCrop()` поддерживает `allowOverflowCanvas`, считает `finalCanvasSize`, `viewportX/Y`, `viewportSize`, `textureScale`.
- Для custom frame `textureScale` сохраняется в `texture.scaleX/Y`, а Dynamic Ring отключается.
- Для обычной manual generation Dynamic Ring включается, но `textureScale` игнорируется и `dynamicRing.scaleCorrection` всегда сбрасывается в `1`, поэтому overflow не используется/не компенсируется.

## Изменения

1. В `scripts/apps/MultiTokenArtManager.mjs` добавить небольшой локальный helper или локальные boolean-переменные для manual generation:
   - `customFrameEnabled = Boolean(customFrameConfig)`;
   - `useManualOverflowCanvas = true` для manual preview/export;
   - `manualCanvasSize = customFrameEnabled ? MANUAL_CUSTOM_FRAME_CANVAS_SIZE : null`.

2. В final export ручной генерации, в вызове `service.createTokenBlobFromSelection()`:
   - оставить `canvasSize: customFrameConfig ? MANUAL_CUSTOM_FRAME_CANVAS_SIZE : null`;
   - заменить `compositionScale: customFrameConfig ? manualPreviewZoom : 1` на `compositionScale: manualPreviewZoom`;
   - заменить `allowOverflowCanvas: Boolean(customFrameConfig)` на `allowOverflowCanvas: true`.

3. В `#renderManualTokenPreview(state)`:
   - передавать в `service.createTokenCanvasFromSelection()` `compositionScale: previewZoom` и `allowOverflowCanvas: true` не только для custom frame;
   - рассчитывать `previewViewportSize` через `metadata.viewportSize` для обоих случаев;
   - рассчитывать `drawScale` как `fitScale`, без дополнительного умножения на `previewZoom`, потому что `previewZoom` уже участвует в compositionScale и metadata;
   - использовать `metadata.viewportX/Y` для обоих случаев.

4. В `#persistGeneratedTokenBlob(...)`:
   - при замене существующего token image оставить запись `scaleX/scaleY = safeTextureScale` только для `customFrameEnabled`;
   - при формировании `targetTokenImage.dynamicRing` выставлять:
     - `enabled: !customFrameEnabled`;
     - `scaleCorrection: customFrameEnabled ? 1 : safeTextureScale`;
     - текущие цвета без изменений.

5. В `#buildGeneratedTokenImage(uploadedPath, sort, { customFrameEnabled, textureScale })`:
   - оставить `scaleX/scaleY` как сейчас: `safeTextureScale` только для custom frame, иначе prototype scale;
   - в `dynamicRing.scaleCorrection` выставлять `customFrameEnabled ? 1 : safeTextureScale`.

6. Не менять `scripts/logic/AutoTokenService.mjs`, если после реализации не обнаружится необходимость: сервис уже корректно возвращает overflow metadata.

7. Не обновлять `CONTEXT.md`, если изменение останется точечным и не меняет архитектуру/manual flow, а только расширяет уже описанное overflow-aware поведение на Dynamic Ring.

## Проверка

1. Статическая проверка кода на синтаксис/очевидные ошибки в измененных участках.
2. Ручная проверка в Foundry VTT v13:
   - manual token без custom frame, с Dynamic Ring: часть изображения/alpha-добавки вне квадрата превью не обрезается после сохранения и применения;
   - manual token с custom frame: поведение не изменилось, Dynamic Ring отключается, масштаб применяется через `texture.scaleX/Y`;
   - manual token без overflow/без увеличенного preview zoom: визуальный результат остается прежним;
   - создание из portrait и замена существующего token image оба сохраняют корректный масштаб.

## Риски

- `previewZoom` станет влиять на non-custom final export как на custom frame. Это соответствует требованию "по аналогии с кастомной рамкой", но стоит проверить UX: колесо превью теперь фактически меняет итоговый Dynamic Ring subject scale.
- Для Dynamic Ring компенсация должна идти через `ring.subject.scale`; поэтому нельзя писать `safeTextureScale` в `texture.scaleX/Y` для non-custom случая, иначе масштаб применится дважды или изменит размер токена на сцене.
